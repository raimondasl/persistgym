# arc/: the pinned ARC-AGI-3 harness and our patches

ARC Prize's harness, [arcprize/arc-agi-3-benchmarking](https://github.com/arcprize/arc-agi-3-benchmarking) (MIT), is a git submodule at `arc/upstream`, pinned at commit `4ca00e607e3364a501fcbf7d1b7537dd2729cec3` (2026-09-21). Our changes are not committed inside the submodule. They live as numbered `git format-patch` files in `arc/patches/`, one concern each, so they can be reviewed, re-applied and offered upstream.

| Path | What it is |

## Setup
```bash
git submodule update --init arc/upstream     # checks out exactly 4ca00e6
uv run arc/apply_patches.py                  # apply all patches, run upstream unit tests
uv run arc/apply_patches.py --each           # ...and test after every patch
uv run arc/apply_patches.py --no-tests       # only check that the series applies (~1 s)
uv run arc/apply_patches.py --keep           # keep arc/.work/patched for inspection
uv run arc/offline_smoke.py --toy            # S0-S4 on the toy game with a stub model ($0, ~1 min)
RUN_OFFLINE_SMOKE=1 uv run pytest -q arc     # root tests including that end-to-end run
```

`apply_patches.py` creates `git worktree add --detach arc/.work/<name> 4ca00e6` from the submodule, runs `git am --committer-date-is-author-date` on every patch with a fixed committer, runs `uv sync --locked` and `pytest tests/unit` there, then removes the worktree unless `--keep` is given. It prints the patch-series SHA-256 and the patched commit and tree IDs. The same series always gives the same IDs. For 0001-0005 on 2026-09-30 these were series `82580ebc…`, commit `b464c55d…`, tree `93573770…`. For 0001-0012 on 2026-10-01: series `855409ae…`, commit `9996462a…`, tree `6f1314e1…` (the tree equals the dev branch the patches were exported from). For 0001-0015 on 2026-10-01: series `ffea2c9c…`, commit `0a8d690c…`, tree `be770327…`. For 0001-0016 on 2026-10-01: series `7ce36bd8…`, commit `ef433150…`, tree `306d2f80…`. For 0001-0017 on 2026-10-01: series `14e25cc7…`, commit `67f6dd0d…`, tree `5206d039…` (these are also in `config_freeze.json`). The 0001-0017 files were exported from the worktree `apply_patches.py --keep` builds (0016 and 0017 committed there with the same fixed committer and their author date as committer date), so each patch's `From <sha>` line is the commit ID that patch gets when applied. ### What the snapshot tests pin down (patches 0005, 0008, 0013 and 0016)
The tests run `BenchmarkingAgent.main()` on a scripted 2×2 game through the real google-genai SDK over `httpx.MockTransport`. The mock provider answers every call with a signed thought step plus visible text, so a leak would show. The tests compare each request's full JSON body:
- **S0:** the system instruction contains the notes sentence. `input` holds only `user_input` and `model_output` text items, never `thought` items, signatures or summaries. The oldest user/assistant pair is dropped once the estimate exceeds `MAX_CONTEXT_LENGTH`. Provider usage ≥ 175k never triggers compaction.
- **S1 and S2:** the same visible-text requests until a turn reports ≥ 175k provider tokens. Before the next turn the harness sends one summary request (system prompt `SUMMARY_SYSTEM_PROMPT`, the whole text history, `max_output_tokens` 8,192); later turns start with the user-role bridge followed by the new observation. No request carries thought steps, signatures or summaries, and `run_meta.json` shows `compaction_count` 1 and `context_trims` 0.
- **Drop-oldest never fires in S1:** with about 12k-character observations and one provider token per character, S0 starts dropping turns above 175k characters while S1 compacts instead; every S1 action request starts with the first observation or a bridge.
- **No trim without usage or at few tokens per character (0016):** with usage unreported, or at about 0.1 provider tokens per character, S1 and S2 send their whole history past `MAX_CONTEXT_LENGTH`, both with a lowered limit (where S0 drops its oldest pair in the same runs) and with the checked-in 1,048,576 (13 observations of about 87.5k characters each, no summary, `context_trims` 0). Without usage, the S2 = S4 parity through overflow recovery (0013) also holds: the provider's rejection is the only thing that compacts either one. The unit tests in `test_manual_rolling_compaction.py` add a tiny `ESTIMATED_CHARS_PER_TOKEN` case and check that `_trim_to_fit_context` is never called with a summary compactor and is called before every request without one.
- **S2 = S4 without thoughts:** removing S4's `thought` steps and the SDK's `annotations` makes every S4 request, including the summary request, equal to S2's. This also holds when a lost life buffers a GAME_OVER frame just before compaction (both summarize that frame; see 09a307b below). S1 equals S2 except the notes sentence. The S2 flag also wins over `analysis_mode`.
- **S4:** every earlier `thought` step (with its `signature`) and `model_output` is replayed as the SDK parsed it. The SDK adds `"annotations": null` to text parts. At the 175k trigger the harness sends one summary request with system prompt `SUMMARY_SYSTEM_PROMPT`, the full native history including thoughts, and `max_output_tokens` 8,192. Later turns restart from a user-role bridge message, and the summary call's own thought is not carried forward.
- **Direct parity (0013):** S0 and S1 send identical requests until S0 trims or S1 reaches its trigger. S2 equals S4 without thought steps across two compactions (the second summary covers the first bridge), through action-request overflow recovery (both summarize without the current observation and resend it after the bridge), and after an unparseable reply (the same request is retried; the rejected reply and its thought are not kept).
- **All configs:** every request has `thinking_level: high`, `thinking_summaries: auto`, `store: false` and (since 0017) `service_tier: standard`, summary requests included. With the tier removed from a config the field is absent; with `flex` or `standard` it is present on every request and the bodies are otherwise unchanged.

## Confirming S4 against ARC's published runs
ARC did not check in a Gemini high Provider Adapter profile, so S4 is a reconstruction. What can be checked from public data:
1. **Config tag and model.** `GET https://arcprize.org/api/sessions/{guid}` returns `"config"` and a `config_…` tag. The published Gemini high Adapter sessions report `"config": "google-gemini-3-8-flash-high-provider-adapter"` and `"model": "gemini-3.8-flash"`; the Standard sessions report `google-gemini-3-8-flash-high`. (Read from session JSON already cached under `results/raw/arc_public/sessions/` in the main checkout, e.g. `0b43e4ff-…` and `484de130-…`.) Our IDs match these tags exactly. The session record carries no request settings.
2. **Per-step metadata in the recordings.** `GET https://arcprize.org/api/recordings/{game_id}/{guid}` holds the action metadata the harness sends with each step: usage, cost and reasoning, plus a `state` block on Provider Adapter runs (`input_items_sent`, history sizes, `harness_compaction` usage and cost). A committed script in the free-analysis track should check, on the published high Adapter runs:
   - **Trigger.** A step's metadata sums its retries, and on the step after a compaction it also includes the summary call. So compute each step's action total as `usage.total_tokens` minus `state.harness_compaction.usage.total_tokens`, when the latter is present. Every compaction should follow a step whose action total is ≥ 175,000. The converse can only be expected on steps without retries, and the metadata does not mark retries.
   - **Summary cap.** `harness_compaction` output tokens never exceed 8,192, and the cap is sometimes hit.
   - **Pricing.** Each step's cost equals `input × 0.75 / 1e6 + output × 3.75 / 1e6`.
   - **Thought summaries.** `reasoning` is non-empty on most steps, which fits `thinking_summaries: auto`.
   - **Native replay.** Between compactions, `input_items_sent` grows by at least 3 per turn (user input, thought, output).
   - **Output cap.** No step exceeds 65,536 output tokens. This is a weak check: it fails only if ARC used a different cap and a step hit it.
3. **Thinking level.** `thinking_level` is not visible anywhere. Indirect check: reasoning tokens per action in our S4 pilot should be in the published high-Adapter range (about 6.1k mean, `docs/background.md` §4) and clearly above the low-Adapter runs.
4. **If any check disagrees,** record the difference in `results/decisions.md`. Either fix S4 before the config hashes are frozen in PREREG, or ask ARC Prize for the exact profile; contacting ARC is the researcher's call.

Steps 1-3 do not show that ARC used `MAX_CONTEXT_LENGTH` 1,048,576, the 8,192 headroom or `max_output_tokens` 65,536. These come from the low profile and are assumed.

## Exit reasons in this harness
`run_meta.json` now always has `exit_reason`. The names are upstream's (`base.py:18-25`). Their meaning in this code, which matters for the PLAN §8.3 re-run rule:
- `GAME_WIN` (`agent.py:736`), `ACTION_BUDGET` (per-level budget at `agent.py:749`, or the total-action fallback at `base.py:117`), `TIME_BUDGET` (12 h wall clock, `base.py:97`).
- `API_ERROR` means an exception while submitting the action to the **ARC** environment (`take_action`). It does not mean a model API error (`base.py:113`).
- `AGENT_ERROR` means any other exception in the loop. This includes the **model** call failing after `MAX_RETRIES` (`agent.py:1098`) and compaction failures.
- `SCORECARD_CLOSED` means an `API_ERROR` agent whose scorecard was closed server-side (404 on close while the card exists; `swarm.py:153-156`). If closing the scorecard fails any other way, upstream marks every agent `API_ERROR`, even winners (`swarm.py:157-160`). With 0001 that is now visible in `run_meta.json`. With 0015, `agent_exit_reason` keeps the ending the agent's own loop recorded (for example `GAME_WIN` or `ACTION_BUDGET`), so the re-run rule can tell a failed scorecard close from an error in the loop.
- `COST_CAP` (patch 0010) means the optional cost guard ended the run. It never fires unless `agent.MAX_RUN_COST_USD` is set.
- With patch 0009, a model call that fails because the 12 h wall clock ran out during a throttling backoff is recorded as `TIME_BUDGET`, not `AGENT_ERROR`. Precisely: a throttled response is passed to the SDK once the next wait would end past the deadline (within 60 s of it, or up to 30 min with a long `Retry-After`), and any later `AGENT_ERROR` in the run becomes `TIME_BUDGET`. The check uses a run-wide counter, so an unrelated `AGENT_ERROR` in that last window is relabelled too. Both are re-run under the PLAN §8.3 rule.
- `UNKNOWN` means the run is still in progress, or the process died before recording an ending.

## Throttling and Flex (patch 0009)
Gemini Flex answers 503 when it is at capacity and 429 for rate limits, and Google says clients must add their own exponential backoff ([Flex inference](https://ai.google.dev/gemini-api/docs/flex-inference), checked 2026-10-01). At the pin, a throttled response gets google-genai's 3 quick retries (about 0.5, 1 and 2 s, `google/genai/_interactions/_base_client.py:772-829`), then `_request_with_retries` retries `MAX_RETRIES` times without waiting (`agent.py:1010-1016`), so 10-15 s of congestion (longer only if the server sends `Retry-After`) ends a run with `AGENT_ERROR`. `ThrottleBackoffTransport` sits below the SDK and retries 429/503 itself, so neither SDK retries nor `MAX_RETRIES` are spent; summary requests are covered too. The path profiles use: first wait 2 s, doubling to 60 s, up to 25% shorter by jitter, never shorter than `Retry-After`, at most 30 min per throttled episode, and never past the run's 12 h deadline. Past either bound the 429/503 goes to the SDK as before. `run_meta.json` records the policy and counters under `transport_retry`. Limits: requests that httpx sends through an environment proxy bypass the wrapper; the async SDK clients are not wrapped (the harness does not use them). The researcher can change the values before the config hashes are frozen.

## Cost guard (patch 0010)
`agent.MAX_RUN_COST_USD` is off in every checked-in profile. Set, it ends a run with `COST_CAP` once the run's estimated spend exceeds the value. The estimate covers all recorded requests (retries and harness summaries included) at the configured `pricing`, with no cache or tier discount, which is ARC's published-cost accounting. Under Flex it is therefore about twice the bill. The check runs before each action, after the win and per-level budget checks, so the action whose request crossed the limit still runs (overshoot ≤ one step). `run_meta.json` records `cost_guard` with the limit and the current estimate. Whether to use it, and at what value, is the researcher's decision (PLAN §16.3, §16.5): a `COST_CAP` ending would be a reported deviation from ARC's protocol.

## Game draw (`draw_games.py`, D15)
`uv run python -m arc.draw_games <freeze-commit-sha>` runs once, after the researcher has merged the frozen PREREG.md. It makes no paid calls and uses no key. Rule: T is the freeze commit's committer time plus 10 minutes, and SEED is `int(outputValue[:16], 16)` of the first NIST Randomness Beacon 2.0 pulse at or after T, from `https://beacon.nist.gov/beacon/2.0/pulse/time/<T in ms>`. If NIST has no such pulse within 24 h of T, SEED comes from the first drand `default`-chain round at or after T (`https://api.drand.sh/public/<round>`, `int(randomness[:16], 16)`). Then `perm = random.Random(SEED).sample(['FT09', 'SB26', 'R11L', 'CD82'], 4)`. `perm[0]` is the truncated-pilot game (D17), `perm[3]` is the game dropped under the 3-game fallback (D32), and SEED + 2 and SEED + 3 order blocks 2 and 3 over the sorted (game, config, replicate) tuples (D18).

The script refuses to run (exit 1) unless all of these hold:
- the checkout is clean;
- the SHA is on origin/main's first-parent history, so it is the PR's merge or squash commit, not a commit inside the merged branch;
- PREREG.md there has `Version: x.y` with x.y ≥ 0.2 and no `-draft` suffix, and a `Status:` line starting with "Frozen" (any case);
- PREREG.md at its first parent is not frozen, so a later commit cannot move T;
- no draw for that commit exists yet.

Other exit codes: 3 means too early (T has not been reached, or NIST has no pulse yet and less than 24 h has passed), so re-run later; 2 means a beacon error. When NIST cannot be reached at all for 24 h or more after T, the drand fallback needs `--fallback-if-nist-unreachable`, and the reason goes in `results/decisions.md` first.

Checks made on the beacon data:
- the pulse's timestamp is at or after T;
- the preceding pulse in the chain is before T;
- drand's `/info` matches the pinned chain hash, period and genesis time;
- drand's `randomness` equals SHA-256 of its `signature`.

The beacons' own signatures are not verified. The raw responses are kept so anyone can verify them. Output goes to `results/draw/<run_id>/`: `meta.json`, `draw.json`, the raw beacon responses (byte-exact; `results/draw/.gitattributes` keeps git from changing their line endings) and `decisions_block.md`, which is also printed for pasting into `results/decisions.md`. The module docstring gives the API sources, checked 2026-10-01.

## Paid runs (`run_path.py`)
**Operator rule: one paid run at a time.** Start a paid run only when no other paid run (ARC or PersistGym) is going, and wait for it to end before the next. Both launchers enforce this with one lock file: this one and the PersistGym launcher (`harnesses/cli.py`, `harnesses/DESIGN.md` §8), which also runs the same ledger and frozen-PREREG checks (`common.approval.require_paid_run`).

Run from the repository root of a checkout of `origin/main` (the approval line and the frozen PREREG must be there). `PERSISTGYM_ALLOW_PAID=1` is set for the one command, never in `.env`. Git Bash syntax:
```bash
# Block 1: payload acceptance check, one minimal request per profile (a few cents)
PERSISTGYM_ALLOW_PAID=1 uv run --env-file .env python -m arc.run_path --approved-block <block> \
    --experiment gemini_probe --acceptance-check --planned-usd 1
# Block 1: truncated pilot on perm[0] of the path games (PLAN §16.3, D17)
PERSISTGYM_ALLOW_PAID=1 uv run --env-file .env python -m arc.run_path --approved-block <block> \
    --experiment arc_pilot --config S0 --game <perm0> --seed 1 --planned-usd <usd> --max-actions 50
#   S1: --max-actions <hard cap> --after-summary-turns 5;  S2: --max-actions 30
# Blocks 2 and 3: one counted run (PREREG §7.4; a re-run adds --rerun-of <run_id>, seed s + 100)
PERSISTGYM_ALLOW_PAID=1 uv run --env-file .env python -m arc.run_path --approved-block <block> \
    --experiment arc_path --config S0 --game ft09 --seed 1 --planned-usd 120
```
In PowerShell, set `$env:PERSISTGYM_ALLOW_PAID = '1'` before the command and remove it after. One invocation is one run: one game × one profile × one seed, or one acceptance check of up to four profiles. `--game` takes `ft09` or a versioned ID such as `ft09-<version>`; the served game ID is recorded.

**What it refuses** (exit 2, before anything is spent):
- a block name that is not exactly `[A-Za-z0-9._-]+` (the guard strips spaces, but the costs row is tagged with the name as given, so a padded name would escape the block's spend); a profile other than S0, S1, S2, S4; a game other than FT09, SB26, R11L, CD82 (the held-out SP80, VC33 and TN36 included: no pilot on a held-out game); a malformed game ID or run ID;
- an `arc_path` run with `--max-actions` or `--after-summary-turns` (counted runs are never truncated), or with `--planned-usd` below $120 (the D22 guard, below); `--after-summary-turns` without `--max-actions`; `gemini_probe` without `--acceptance-check` or the reverse; any `statecarry_*` experiment (phase 2, not supported yet);
- a profile in the freeze record that does not request `service_tier: standard`, or whose configured prices differ from `pricing.py`; a date after 2026-12-31, when the price table expires (Gemini 3.8 Flash prices double);
- `GOOGLE_API_KEY` unset, or `ARC_API_KEY` unset for a game run (only presence is checked; keys are never printed or written);
- the paid-run lock held by another run, or kept by a run whose spend could not be written to `costs.csv`;
- the last paid run's costs row missing from this checkout's `results/costs.csv` (the lock is shared by every checkout, the ledger is not), or a `costs.csv` that cannot be read;
- the paid guard (`common.approval.require_paid_approval`): `PERSISTGYM_ALLOW_PAID` not `1`; no valid line `approved_block: <name> | experiments: <list> | max_usd: <n>` identical in `results/decisions.md` on `origin/main` (fetched now), HEAD and the working tree; the experiment not in the line's list; block spend + planned spend above `max_usd`; no headroom under the phase cap; an unreadable `costs.csv` row;
- PREREG.md uncommitted, not the same blob in HEAD as on `origin/main`, or not frozen (`Version:` at least 0.2 without `-draft` and a `Status:` line starting "Frozen": `common/prereg.py`, the rule `draw_games.py` and the PersistGym launcher use);
- the patch files, the patched commit or tree, or a resolved profile's hash differing from `config_freeze.json`.

**What a run does.** It applies the series in `arc/.work/paid` (removed afterwards unless `--keep-worktree`), checks it against the freeze record, and starts `run_path_inner.py` with the patched harness's interpreter in a short scratch directory under the system temp folder. The inner process gets a sanitized environment (no other keys, no provider or ARC settings, no `OPERATION_MODE`) plus only `GOOGLE_API_KEY` and, for a game, `ARC_API_KEY`. A game run is ARC's own `Swarm`, online, as `main.py` runs it (`ROOT_URL` `https://arcprize.org`; the arc-agi client's default API host, `ARC_BASE_URL` never set), with one scorecard tagged `persistgym`, the experiment, the profile, `seed-<n>` and the run ID. It adds three things that change no request body: each model HTTP request is timed into `calls.jsonl` (status and seconds only); the harness cost guard (patch 0010) is set; and the optional truncation. The acceptance check sends, per profile, one request through the harness's own adapter with the profile's request settings and system prompt and the user message "This is a connectivity check, not a game. Reply with one word: ready." It plays no game and uses no ARC key.

**Spend limits.** Before the run, the guard requires block spend + planned spend ≤ `max_usd`. During the run, the harness cost guard counts ARC's no-cache list cost of every recorded request and stops the run with `COST_CAP` once it exceeds the limit, checked before each action. The limit is `--planned-usd` for a pilot or check, and D22's $120 for a counted run, which is why `arc_path` needs `--planned-usd` ≥ 120. List cost is at least the billed estimate, so a run spends at most its planned amount plus one model call. The guard is set by the launcher at run time, not in the profiles, so the config hashes do not cover it; `meta.json` (`cost_cap_usd`) and `run_meta.json` (`cost_guard`) record it per run. A consequence for planning: every counted run needs $120 of room both in its block's `max_usd` and under the phase 1b cap, whatever it is expected to cost, so the last runs of a block or of phase 1b are refused once less than $120 is left.

**Truncation (pilot only).** `--max-actions N` ends the run with `ACTION_BUDGET` before action N + 1. `--after-summary-turns M` ends it once M steps have been saved from the first harness summary on (S1's "first compaction plus 5 turns", PLAN §16.3), with `--max-actions` as the hard cap. `result.json` records which rule fired. Pilot runs are never counted (PLAN §11).

**Seeds.** `--seed` labels the replicate (PREREG §7.4: replicates 1 and 2; the re-run of replicate s gets s + 100 and `--rerun-of`). It is recorded in `meta.json` and the scorecard tags and is never sent to the model: the harness sets no sampling seed.

**Outputs.**
- `results/raw/<experiment>/<run_id>/` (gitignored): the harness run directory as `harness/` (`run_meta.json`, `step_NNN.json`, `compaction_NNN.json`), the ARC recording, `result.json` (scorecard ID and scorecard, served game ID, exit reason, truncation), `calls.jsonl`, `config.json`, `harness.log` (the harness's INFO log, which is also printed), and for the check `accept.json`.
- `results/<experiment>/<run_id>/meta.json`, written by `common.runmeta` (commit it): `config_hash` (equal to the frozen hash) and `config_freeze` (hashes, series, commit, tree, pin), `exit_reason` and `agent_exit_reason`, `reported_models`, `service_tier` requested and served (counts per tier the steps report), `latency` (median, p90 and max seconds per successful model call), tokens, list and billed cost with the price source, wall clock, compactions, `context_trims`, `transport_retry` counters, the cost guard, the block, phase and planned spend. For `arc_path` it also holds `outcome` (scorecard ID, served game ID, steps), and ARC's scorecard is written next to it as `scorecard.json`. ARC's scorecard model has an `api_key` field that the API response could fill, so every field whose name looks like a credential is dropped from the scorecard (in `result.json` too), and the launcher replaces any key value it still finds in `meta.json` or `scorecard.json` and warns.
- One `results/costs.csv` row per run in which any model request was made, tagged `approved_block=<name>;` in `notes` (how the guard sums block spend), followed by the run, its exit reason and `git_dirty`. `provider` google, `api` interactions, `service_tier` the requested tier, `service_tier_served` the tiers the responses report. `n_calls` counts successful model responses; `input_tokens` include cached tokens; `output_tokens` include thinking tokens, which are also given as `reasoning_tokens`; `latency_s` is the median seconds per successful call.
- The launcher accounts for the run whatever happens: after a crash or Ctrl+C it still copies what the harness wrote, appends the costs row and writes `meta.json`. Ctrl+C also reaches the inner process, which runs `Swarm.main` in a thread it polls, as `main.py` does (a plain `Thread.join()` cannot be interrupted by Ctrl+C on Windows), and closes the ARC scorecard; the launcher waits up to 120 s for that, then kills the inner process tree (`taskkill /T` on Windows, since killing `uv run` alone leaves its python child running). A second Ctrl+C kills the tree at once. If the accounting itself fails, it says so and leaves the paid-run lock held with the reason, so no paid run starts until the costs row has been added by hand and the lock file deleted.

**Costs** (`pricing.py`: one table, source https://ai.google.dev/gemini-api/docs/pricing checked 2026-09-30, the same numbers as `analysis/data/prices.csv`). Usage comes from each `step_NNN.json` and `compaction_NNN.json` (accepted and retried attempts), plus any usage that only `run_meta.json`'s `total_usage` holds, such as a failed summary request; that part is flagged in the row's notes. The list cost prices all input at $0.75/M and output, thinking included, at $3.75/M: ARC's no-cache accounting, and what the harness cost guard counts. The billed estimate prices uncached input at $0.75/M, cached input at $0.075/M and output at $3.75/M: the standard tier as billed (D21, D23). A step whose served tier is not `standard` is priced at standard and flagged.

**Pilot blinding** (PREREG §11, accepted technical choice "pilot outcomes only in results/raw"). For `arc_pilot`, the committed `meta.json` and costs row hold no game outcome: a `GAME_WIN` or `ACTION_BUDGET` ending reads `NORMAL_ENDING_BLINDED` (errors, `TIME_BUDGET` and `COST_CAP` stay visible), `reasoning_tokens` is left empty, and there is no `outcome` block, scorecard or truncation detail. The console summary follows the same rule. Everything stays in `results/raw/`.

**The lock.** `persistgym-paid-run.lock` in the git common directory (the main checkout's `.git/`, shared by all its worktrees; `common/paidlock.py`), taken by this launcher and by the PersistGym launcher. It is taken before the spend checks, so two runs cannot both pass them, and released when the run ends. A run that dies without cleaning up leaves it behind, and so does a run whose spend could not be written to `costs.csv` (on purpose, with the reason in the file): the next paid run refuses and prints its contents. Check that no paid run is still going and that `costs.csv` has every paid run's row, then delete the file by hand. Nothing removes it automatically. Next to it, `persistgym-paid-last-run.json` names the last run that appended a costs row (its run ID and the row's `timestamp_utc`, since a PersistGym `--run-id` can be reused) and the `costs.csv` it went to; a paid run in a checkout whose ledger lacks that row refuses, so run from one checkout or bring the row over first.

**$0 check of the inner modes.** `uv run arc/run_path_offline.py` (or `RUN_OFFLINE_SMOKE=1 uv run pytest -q arc`) builds the patched harness and runs `run_path_inner.py` offline on the toy game with the stub model of `offline_smoke_inner.py` behind its socket guard: `play` S0 with `--max-actions 4`, `play` S1 with `--max-actions 50 --after-summary-turns 3`, and `accept` for all four profiles. Then it applies the launcher's own collect and accounting functions and checks that every request asks for the standard tier at high thinking, that the call meter saw exactly the stub's requests, that the cost guard was set, and how each run ended. On 2026-10-01 all three passed: S0 stopped after 4 actions, S1 summarized before step 3 and stopped after 3 more steps (6 calls), and all four profiles were accepted. The only differences from a paid run are offline play, the skipped online-only check and the stub transport below the call meter.

**Not tested.** The launcher has never run for real, and nothing here has played online. The online path in `run_path_inner.py play` is ARC's own `Swarm` and `arc_agi` online client, which differ from the offline check in operation mode and transport only. The first real use is block 1's acceptance check.

## Safety
- **No paid calls.** Every test uses fake adapters or `httpx.MockTransport`. Live tests skip unless `RUN_*_LIVE_TESTS=1` is already set.
- **No `.env` loading.** The upstream `tests/conftest.py` and live tests call `load_dotenv()` with no path. python-dotenv 1.1.1 (pinned upstream) then searches the calling file's directory and its parents, so from `arc/upstream/tests` it would find a `.env` at the repository root. This was checked offline with a throwaway `.env`. `apply_patches.py` therefore loads `no_dotenv_plugin.py` (`-p no_dotenv_plugin`). It also drops every variable that looks like a credential, every provider-prefixed variable (`OPENAI_`, `GOOGLE_`, `GEMINI_`, `ARC_`, …), and `RUN_*_LIVE_TESTS`. If you run `pytest` inside `arc/upstream` by hand, do it only when no `.env` exists above it.
